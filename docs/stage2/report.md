## 1 项目目标

第一阶段主要解决“创建一份问卷并收集回答”的问题，题目作为问卷的子对象保存。这样的结构适合一次读取整份问卷，但当同一道题要放进多份问卷时，就需要反复创建，也难以记录题目的版本和来源。

需求变更提出了八项能力：保存常用题目、共享给他人使用、改题不影响旧问卷、查看历史和恢复、多版本并存、查询使用情况、管理题库，以及跨问卷查看单题统计。我最先关注的是：怎样增加这些功能，同时保留第一阶段已经做好的问卷和收集的数据。

因此，我在讨论中提出三个约束：旧答卷仍要按当时的题目解释；题库中的更新不能直接改变已发布问卷；共享题目不能顺带开放他人的答卷。这些约束影响了后续的数据模型、权限判断和测试样例。公共题库、个人标签和批量快照派生是我们讨论中增加的受控扩展，与实验原文的八项要求分别说明。

## 2 系统设计与第一阶段演进

我没有把第二阶段理解成重新写一个题库网站，而是要求在原问卷编辑、填写、跳转、校验和统计流程上扩展。原有MongoDB、FastAPI、PyMongo、Jinja和原生JavaScript技术路线继续保留，界面也沿用第一阶段的风格。

讨论后，系统把可复用题目与问卷中的题目实例分开：题库负责管理编辑稿、正式版本和授权，问卷负责保存明确版本的内容快照。统计再通过独立的范围入口筛选“我的问卷”。我提出这个范围应该单独封装，是为了以后扩大范围时能够集中修改授权规则，而不是到每一条聚合中分别补条件。

按照实验要求，我把这次演进整理为下面八点。表中是讨论后采用的设计，具体程序由AI实现。

| 演进要求 | 我的理解与最终调整 |
| --- | --- |
| 第一阶段设计是什么 | 题目嵌入问卷，答卷独立保存；发布后按问卷版本读取稳定定义，草稿更新已有修订号检查。 |
| 新需求带来什么问题 | 原来的题目没有独立身份，复制文字不能可靠表示共享、来源或版本，也无法确定哪些跨卷答案应合并。 |
| 为什么修改原设计 | 我追问过“选用是引用还是复制”。最后采用引用明确版本、同时固化问卷快照，使复用和旧问卷保护能够同时成立。 |
| 修改了哪些部分 | 增加题库模块、版本与授权接口、题库页面、来源绑定和跨卷统计；原问卷保存、选用、升级和发布接入一致性校验。 |
| 数据结构如何变化 | 新增独立题目、版本、版本状态、授权、个人收藏、使用记录及操作回执；问卷保留原题目内容，另外增加questionRefs来源元数据。 |
| 程序如何调整 | 编辑稿与正式版本保存成为两个动作；选用、升级、发布等写入按业务动作进入事务，跨卷查询统一使用本人范围和精确版本。 |
| 兼容性问题 | 原严格题型结构不能随意加入来源字段；原全量PATCH需要防止伪造快照；旧匿名键只能用于本卷去重，不能直接跨卷计算人数。 |
| 如何保证旧功能可用 | 保留原题目实例、选项、跳转和答案，通过迁移补充来源；同时检查旧数据BSON、原统计、完整回归和恢复结果。 |

详细模块见[系统架构](architecture.md)，八项需求与实际范围见[需求对照](requirements.md)。

## 3 MongoDB设计

我认为这次最关键的变化是区分“题目本身”“题目的某一版内容”和“它在一份问卷中的某一次使用”。如果只保留一个题目ID，就难以同时解释版本更新和同卷重复选用。因此，系统分别保存独立题目、精确版本、来源关系和问卷实例身份。

| 数据 | 保存方式与原因 |
| --- | --- |
| 题目管理记录 | questions保存所有者、可修改的workingContent、revision及版本指针，用于管理当前编辑状态。 |
| 正式内容与可选状态 | question_versions只插入正式内容；question_version_state单独保存是否允许新选用，避免下架操作改动历史正文。 |
| 共享与个人整理 | question_grants保存指定授权，question_bookmarks保存本人的收藏和标签；整理标签不回写共享源题。 |
| 使用与重试结果 | question_usage记录实际发生的累计使用，operation_receipts保存幂等回执，支持网络重试。 |
| 问卷与答卷 | surveys继续嵌入完整题目快照并记录questionRefs；responses独立保存，让答卷能够持续增长。 |

我采用MongoDB的一个原因是，四种题型的选项、校验配置和跳转规则可以自然表示为BSON对象和数组。问卷填写时通常一起读取全部题目，嵌入完整快照便于得到稳定定义；即使源题归档或共享被撤回，原问卷仍能解释旧答案。

不过，版本、授权和答卷有各自的生命周期，不能把全部历史都嵌入一个无限增长的问卷文档。因此这些部分独立保存，通过ID关联。与把每个选项、校验项和跳转条件拆成关系表相比，这种方式减少了整卷读取时的逐表组装；但我也提醒过，MongoDB没有替应用完成外键和所有权检查，关联、权限及内容一致性仍要由代码保证。

并发写入使用真实副本集事务。保存正式版本时，版本、管理指针、状态与回执在同一事务提交；选用或升级时，问卷快照、引用与使用记录保持一致。revision检查负责拒绝过期修改，唯一索引和幂等回执分别处理重复版本与网络重试。JSON Schema负责结构约束，不能代替当前用户鉴权。完整字段、索引及三项MongoDB设计说明见[数据库设计](database.md)。

## 4 跳转设计

我要求第二阶段继续使用第一阶段已经验证过的跳转流程。跳转仍然指向当前问卷中的实例，支持单选、多选、数字条件，以及默认进入下一题或结束填写；服务端会重新计算实际路径，而不是完全相信前端传来的经过题目。

题库中的通用版本不携带原问卷的jumpRules。我的理解是，同一道题放进不同问卷后，后续题目的位置和含义可能不同，原问卷的跳转不应直接复制过去。因此，新选入时从空跳转开始，由当前问卷配置规则。

草稿问卷显式升级题目版本时，保留原实例ID和当前问卷规则，并重新校验整份定义。如果新版题型或选项让旧跳转条件失效，就拒绝本次升级，由使用者处理规则。已发布问卷的内容与跳转继续冻结。我在基础问卷中实际测试了从第1题直接跳到第4题，并确认被跳过的必答题不会阻止提交。

## 5 校验设计

我在验收时比较关注边界输入，因为界面能填完一份正常问卷，并不能说明校验规则可靠。第一阶段的四题型校验继续保留，第二阶段则在来源、版本和权限方面增加检查。

| 校验对象 | 我参与确定或实际检查的规则 |
| --- | --- |
| 单选与必答 | 空答不能通过必答校验；必答只对实际经过的题目生效。 |
| 多选 | 最少与最多数量共同生效；基础样本要求恰好选2项，0、1、3项被拦截。 |
| 文本 | 去除首尾空白并统一字符形式后计算字数；基础样本设置2～6字，检查不足和超长输入。 |
| 数字 | 使用十进制字符串和Decimal128进行精确校验；基础样本要求0～120整数，0和120在预览中均能通过，负数、超上限、小数和非数字被拦截。 |
| 版本与来源 | 选用必须指定明确versionId；该版本必须属于目标题目，问卷快照内容与来源版本一致。 |
| 权限与写入 | 管理请求不能自行指定owner或root；只有维护者可修改原题，批量快照派生只接受最多五个本人实例。 |

我还要求把共享使用权与答卷访问权分别校验：接收者能使用共享题，但不能看到作者的未公开编辑稿，也不能因此查看作者问卷的答卷。搜索、版本历史、来源、使用情况和统计各自按权限过滤。

统计同样需要校验口径。数字0是有效答案，跨卷均值按全部有效答案高精度求和后再除，不把各问卷的均值简单平均；本人已答定义如果缺少来源映射，应明确报错，而不是把漏算显示成0。接口和错误说明见[API文档](api.md)，具体业务边界见[关键规则](rules.md)。

## 6 AI使用过程

第二阶段开始时，我先要求AI对照原始需求、需求变更和第一阶段系统分析差异，再讨论方案。我特别强调旧代码和旧数据要继续保留，并提出“老数据怎么办”，要求迁移和旧功能验证进入执行计划。需求尚未明确时，我要求先商量清楚，在实现前参与关键设计判断，再让AI落实。

| 实验要求 | 我的实际参与和分工 |
| --- | --- |
| AI帮了我什么 | 我让AI帮助核对需求、比较设计、落实集合与接口、编写前后端和测试、执行迁移与恢复，并整理证据。我提出问题和修订意见，再由AI把确定的规则落实为程序。 |
| AI做错了什么 | 初期方案把“不建正式版本”和“修改暂留页面”混在一起，我提出持久编辑稿与正式版本应拆开。实现中还出现测试夹具、UUID替换、错误码断言及浏览器等待问题，这些由AI定位修复，原始失败记录保留。 |
| 我改了什么 | 我修改了需求解释和方案边界，要求补上旧数据、共享撤回、权限、实例身份和统计口径，并参与前段真实测试、提交截图和反馈；具体源代码修订由AI完成。 |
| 我设计了什么 | 我提出或推动了编辑稿与版本分离、统计范围独立封装、root溯源落库、公共题维护、个人标签题库、受限使用计数、撤权后真复制和双实例人数口径；具体字段、函数与测试在讨论后由AI实现。 |

我首先追问题目选用究竟是引用还是复制：源题被删除后，旧问卷怎么办，谁有修改权限？我还指出独立题目会增加版本、共享、使用记录的复杂度，同一题在同卷出现两次也必须区分实例。这些问题推动了“引用明确版本并固化完整快照”的方案。我提出把“可见问卷筛选”单独抽出，首版固定为我的问卷；`rootQuestionId`现在就保存，避免以后无法追踪来源。最终root只用于溯源，不能扩大权限或自动合并统计。

对于“改题不影响旧卷”和“修改时决定是否生成新版”，我建议管理记录保留可覆盖的当前内容，显式保存才生成正式版本；题目一旦被已发布问卷引用，后续内容保存必须生成新版。我也提出公共题应有指定维护者，普通用户只选用或派生，选用接口必须明确`versionId`，归档不能破坏旧快照。我用“你多少岁了”和“你的年龄是”的例子追问怎样定义同题，最终采用ID、版本和来源关系，搜索只辅助查找，不按文字或语义自动归并。

题库组织上，我要求比较“可共享容器”和“个人分组标签”，倾向先做标签方案，把精力放在版本、引用和统计。后续若升级共享容器，仍需补充身份映射和授权，不能把“以后可扩展”理解成零迁移。我还建议使用页只列自己的问卷明细，维护者另看其他问卷历史累计数；累计按不同问卷去重，不因移除实例而减少。这一计数最终保留维护权限检查，并非聚合数字就可以无条件公开。

共享与统计的边界也是我反复检查的部分。我要求撤回共享后的派生必须是真复制，副本正文和鉴权不依赖源题，来源只作追溯，并建议从既有快照批量创建副本。我指出同一答卷回答两个实例时不能把一个填写者算成两人，要求区分回答次数、答卷数和本卷去重账号数，不提供跨卷总去重人数或合并答卷明细。讨论后进一步按本系统匿名也须登录、同卷有稳定身份键的实际情况细化计数。

并发方面，我围绕AI给出的乐观锁与事务方案，补充了权限前置、唯一约束、幂等和事务边界的检查意见，确认管理修订号与内容版本号不能混用，也关注问卷选用和使用记录的一致性。讨论中“事务回滚会消耗版本号”“仅改变事务内写入顺序就能避免半写”的理由经过核对被修正：正确事务应全成或全败。这些是方案讨论的修正，不是AI已经实施过的生产故障。

验证时，我按分组步骤亲自操作前段注册、配置、预览、正式提交、版本和共享测试，反馈空答、无效输入、0与120边界等结果并提供截图。后来页面关闭，我明确要求AI接手剩余测试；后续副本、E双实例和旧页保存冲突由AI执行，撤回及部分标签步骤采用业务服务调用。我的主要作用是提出问题、审查取舍、要求修订和参与验收；代码、自动回归、数据库迁移及技术修复由AI完成。完整建议与采用情况见[详细AI使用说明](ai-use.md)，工具、提示词、代码产物和修订过程见[AI日志](ai-log.md)，实际操作归属见[真实测试记录](manual-acceptance.md)。

## 8 遇到的问题

需求分析时，我最早卡住的是第三条“修改题目不能影响已发布问卷”和第六条“修改时可以决定是否创建新版本”如何同时满足。只说“正式保存才建版”还不够，因为前端暂留输入和后端持久保存不是一回事。后来我们明确了编辑稿、正式版本和发布引用后的强制建版边界，这也是我对AI初期方案提出的一项重要修订。

另一个问题是“同一道题”的含义。我用“你多少岁了”和“你的年龄是”追问过语义相同是否就应合并统计。最后我接受用ID、版本和来源关系表达身份，搜索只帮助查找。这样需要用户明确选用，但能避免数据库把不同题目或不同校验规则的答案误合并。

实现中也有一些问题超出了最初的表面流程：原题型结构不允许随意塞入来源字段；仅增加选题接口，仍挡不住旧整卷PATCH绕过来源；只在事务外检查一次共享权限，也挡不住撤回与选用竞争。原环境没有启用副本集，备份核对原来只覆盖四个集合，也需要随着新模型一起调整。这些代码和环境问题由AI排查、修复，我主要检查处理结果是否符合已经讨论的规则。

交付后的复查还发现了下面几类具体缺陷，失败与修复记录保留在[功能复查报告](recheck-2026-10-26.md)和[AI日志](ai-log.md)中。

| 问题 | 最后的处理与验证 |
| --- | --- |
| 异常Unicode或超大整数可能在编码、存储边界形成500 | 补充输入规范化和拒绝路径，返回明确校验错误，并检查失败请求没有写入。 |
| 停止新选用与本人已持有快照的访问边界混淆 | 分开判断源版本访问和本人问卷历史统计，保留合法旧结果。 |
| 收藏整理可能返回404但标签已经写入，归档后也可能错误限制已有标签整理 | 将响应投影与标签写入放入同一事务，并区分整理已有收藏和新增收藏、换版本。 |
| 保存期间继续输入被响应覆盖，旧编辑页可能覆盖新内容 | 保存期间限制继续编辑，失败保留输入；后段由AI通过两个预先打开的编辑页验证冲突与版本数量。 |
| 历史关联缺失时误取最新版，或按相同文字把不同题目错误映射 | 绑定与迁移同时校对题目、版本、root和快照，不按内容相同认定同题。 |

我自己的操作反馈也需要判断原因。比如“没有找到回答校验”，最后确认是我之前建的题仍为单选，左侧选择新增多选不会改变已有题型；另一次修改说明为空，我确认是自己忘填。报告中保留这些过程，没有把操作问题都写成程序缺陷。

讨论中，我对事务回滚和写入顺序的部分理解也被纠正。正确事务会整体回滚，不能把“先更新指针、后插入版本”直接判断为必然半写。这让我意识到，审阅AI方案时既要敢于提出问题，也要继续核对自己给出的技术理由。

## 9 解决方法、实现边界与实验体会

最后的设计用持久编辑稿、不可变正式版本和问卷快照分别处理编辑、发布与历史数据。我提出的旧数据兼容、共享撤回、实例身份和统计范围问题，也分别落实到了来源元数据、事务边界和验收样本中。恢复旧版本时生成新版本，而不是把指针倒回后删除中间历史；派生题保留来源，但正文和所有权属于新题。

我特别要求保留第一阶段的账号、问卷与答卷。正式迁移从停写后的备份恢复到独立副本集，再执行dry-run、apply、重复迁移及前后核对，原27017库继续保留。原8份问卷共25个实例补充来源，旧答案不重写；测试前12个业务集合的原始文档子集及10份统计也有后续完整性证据。迁移操作由AI执行，我把这些结果纳入验收，而不是只看新题库页面是否出现。

这次我也作了一些范围取舍：题库先采用个人收藏和标签；跨卷默认只统计本人问卷中的精确版本；不自动合并同义题、不同版本或派生题；不提供跨卷总去重人数、合并答卷明细或导出。标签以后若升级为共享容器，仍然需要身份、成员和授权迁移；单节点副本集用于本机事务演示，不把它描述成生产高可用方案。

对我来说，第二阶段最有价值的部分是把模糊的使用反馈转化成能够实现和检查的规则。例如，“改题不能影响旧卷”要落到固定版本和完整快照，“同一道题的统计”要先明确身份和权限，“一个人回答两次实例”则要求把回答次数、答卷数和账号数分开。AI承担了大量实现工作，我的作用是持续提出这些问题、比较取舍、修订边界，再通过具体样本检查结果。
