## 1 项目目标

原系统以问卷为管理单位，题目嵌入问卷，适合一次读取和冻结，但不能独立保存复用，也没有跨用户题目授权、版本来源和跨卷身份。需求变更提出八项能力：保存复用、共享、保护旧卷、历史恢复、多版本并存、使用情况、题库和跨卷单题统计。

本阶段目标是在保留原代码和数据的基础上增加这些能力。修改既有系统的关键约束是：旧答案继续按原版本解释，题库更新不能改变已发布问卷，题目共享不能扩大他人回答访问权。公共题库、个人标签及有界批量快照派生来自项目讨论，作为受控扩展实现，不冒称原文单列要求。

## 2 系统设计

原同步分层继续保留。题目库服务负责编辑稿、不可变版本、权限、回执和事务；来源绑定服务把明确版本固化到原问卷实例；统计范围服务统一决定哪些问卷可以计算；跨卷服务只汇总精确版本。新模板和脚本沿用清爽专业视觉，没有另建成品问卷框架或第二套填写引擎。

| 演进要求 | 实际设计与改动 |
| --- | --- |
| 第一阶段设计是什么 | 问卷内嵌题目，答卷独立，按问卷版本读取定义，原CAS控制草稿编辑 |
| 新需求带来什么问题 | 内嵌题缺独立身份，无法可靠共享、追踪版本、查询来源或合并跨卷回答 |
| 为什么修改原设计 | 直接复制文字丢失身份，直接引用最新内容破坏冻结，需要独立版本加快照 |
| 修改了哪些部分 | 新题库/API/页面/来源绑定/统计scope/迁移及测试，原问卷保存和发布接入来源校验 |
| 数据结构如何变化 | 增加questions、versions、state、grants、bookmarks、usage和receipts，问卷新增questionRefs |
| 程序如何调整 | 保留旧实例和提交协议，新增编辑稿/正式版本动作、事务guard、来源一致性与精确汇总 |
| 兼容性问题 | 旧严格题型字段不能随意加来源；旧全量PATCH可能伪造快照；旧匿名键不能跨卷去重 |
| 如何保证旧功能可用 | 元数据与内容分离，旧答案不重写，回归测试及真实备份/迁移/逐BSON和统计核对 |

详细模块见[系统架构](architecture.md)，原文对应见[需求范围](requirements.md)。

## 3 MongoDB设计

题目管理记录保存可变workingContent和revision，正式内容版本独立保存且不可覆盖；版本可选状态另存，允许下架而不修改历史正文。独立题目、精确版本、root来源、直接来源和问卷实例分别有明确身份。根关系不产生权限，默认统计只按精确版本。

问卷继续嵌入完整快照并保存questionRefs。填写时一次取得稳定定义，不逐题依赖源题或最新版本。答案继续独立增长，旧responses保持原BSON和幂等语义。个人标签保存于本人bookmark，不回写共享源题；usage保存真实累计使用，覆盖起点明确；回执保存网络重试结果。

采用MongoDB是因为异构题型与配置自然对应BSON对象和数组，整卷读取与冻结适合嵌入快照，唯一索引、条件更新和聚合可表达身份、并发及频数。独立生命周期的版本、授权和答案使用引用，避免把所有历史和回答塞到一个文档。与照搬关系结构相比，减少对选项、配置和跳转的逐表组装；但仍显式维护关联与权限，不能因为没有外键就放弃校验。

跨文档写入使用实际副本集事务，同session提交指针、版本、状态及回执。选用、归档、下架、撤权写共同guard产生冲突；普通编辑稿和发布争用hasPublishedUsage与revision。JSON Schema约束结构，不能代替当前用户鉴权。字段、索引、事务边界和三项设计说明见[数据库设计](database.md)。

## 4 跳转设计

沿用第一阶段配置式跳转及服务端路径重放，支持单选、多选、数字条件和默认下一题/结束。实例ID不改，跳转目标仍是本问卷实例，不使用独立题目ID。

通用版本不携带原问卷jumpRules，选入新卷从空跳转开始。手动升级保留实例ID和当前问卷规则，重新验证整卷；新版选项或题型使条件失效时整次拒绝，不默默删除或改成默认路径。发布后快照与规则继续冻结。

## 5 校验设计

四题型内容与答案校验继续复用原实现，保留必答与正下限共同生效、跳过不强制回答、Unicode规范化、十进制字符串和Decimal128精确范围。跨卷数字平均使用高精度求和后一次除法，0有效，不以各卷均值再平均。

新增校验包括：编辑稿保存与正式版本生成分离；来源版本必须属于目标题目；选用明确versionId；管理请求不能指定owner/root；已关联实例的内容hash必须与版本一致；原整卷/单题写入不能绕过来源；发布和hasPublishedUsage同事务；批量快照派生只接受最多五个本人实例。

共享接收者看不到未公开稿，非维护者不能读取下架源版本。搜索、历史、来源、使用情况和答案统计分别按权限过滤。跨卷统计检查本人已答定义映射完整性，不把漏算显示为0。API和错误见[API说明](api.md)，口径见[关键规则](rules.md)。

## 6 AI使用过程

第二阶段开始时，我先要求AI对照原始需求、需求变更和第一阶段系统分析差异，再讨论方案。我特别强调旧代码和旧数据要继续保留，并提出“老数据怎么办”，要求迁移和旧功能验证进入执行计划。需求尚未明确时，我要求先商量清楚，在实现前参与关键设计判断，再让AI落实。

| 实验要求 | 我的实际参与和分工 |
| --- | --- |
| AI帮了我什么 | 我让AI帮助核对需求、比较设计、落实集合与接口、编写前后端和测试、执行迁移与恢复，并整理证据。我提出问题和修订意见，再由AI把确定的规则落实为程序。 |
| AI做错了什么 | 初期方案把“不建正式版本”和“修改暂留页面”混在一起，我提出持久编辑稿与正式版本应拆开。实现中还出现测试夹具、UUID替换、错误码断言及浏览器等待问题，这些由AI定位修复，原始失败记录保留。 |
| 我改了什么 | 我修改了需求解释和方案边界，要求补上旧数据、共享撤回、权限、实例身份和统计口径，并参与前段真实测试、提交截图和反馈；具体源代码修订由AI完成。 |
| 我设计了什么 | 我提出或推动了编辑稿与版本分离、统计范围独立封装、root溯源落库、公共题维护、个人标签题库、受限使用计数、撤权后真复制和双实例人数口径；具体字段、函数与测试在讨论后由AI实现。 |

我首先追问题目选用究竟是引用还是复制：源题被删除后，旧问卷怎么办，谁有修改权限？我还指出独立题目会增加版本、共享、使用记录的复杂度，同一题在同卷出现两次也必须区分实例。这些问题推动了“引用明确版本并固化完整快照”的方案。我提出把“可见问卷筛选”单独抽出，首版固定为我的问卷；`rootQuestionId`现在就保存，避免以后无法追踪来源。最终root只用于溯源，不能扩大权限或自动合并统计。

对于“改题不影响旧卷”和“修改时决定是否生成新版”，我建议管理记录保留可覆盖的当前内容，显式保存才生成正式版本；题目一旦被已发布问卷引用，后续内容保存必须生成新版。我也提出公共题应有指定维护者，普通用户只选用或派生，选用接口必须明确`versionId`，归档不能破坏旧快照。我用“你多少岁了”和“你的年龄是”的例子追问怎样定义同题，最终采用ID、版本和来源关系，搜索只辅助查找，不按文字或语义自动归并。

题库组织上，我要求比较“可共享容器”和“个人分组标签”，倾向先做标签方案，把精力放在版本、引用和统计。后续若升级共享容器，仍需补充身份映射和授权，不能把“以后可扩展”理解成零迁移。我还建议使用页只列自己的问卷明细，维护者另看其他问卷历史累计数；累计按不同问卷去重，不因移除实例而减少。这一计数最终保留维护权限检查，并非聚合数字就可以无条件公开。

共享与统计的边界也是我反复检查的部分。我要求撤回共享后的派生必须是真复制，副本正文和鉴权不依赖源题，来源只作追溯，并建议从既有快照批量创建副本。我指出同一答卷回答两个实例时不能把一个填写者算成两人，要求区分回答次数、答卷数和本卷去重账号数，不提供跨卷总去重人数或合并答卷明细。讨论后进一步按本系统匿名也须登录、同卷有稳定身份键的实际情况细化计数。

并发方面，我围绕AI给出的乐观锁与事务方案，补充了权限前置、唯一约束、幂等和事务边界的检查意见，确认管理修订号与内容版本号不能混用，也关注问卷选用和使用记录的一致性。讨论中“事务回滚会消耗版本号”“仅改变事务内写入顺序就能避免半写”的理由经过核对被修正：正确事务应全成或全败。这些是方案讨论的修正，不是AI已经实施过的生产故障。

验证时，我按分组步骤亲自操作前段注册、配置、预览、正式提交、版本和共享测试，反馈空答、无效输入、0与120边界等结果并提供截图。后来页面关闭，我明确要求AI接手剩余测试；后续副本、E双实例和旧页保存冲突由AI执行，撤回及部分标签步骤采用业务服务调用。我的主要作用是提出问题、审查取舍、要求修订和参与验收；代码、自动回归、数据库迁移及技术修复由AI完成。完整建议与采用情况见[详细AI使用说明](ai-use.md)，工具、提示词、代码产物和修订过程见[AI日志](ai-log.md)，实际操作归属见[真实测试记录](manual-acceptance.md)。

## 8 遇到的问题

原需求第三条要求改题不影响发布问卷，第六条允许决定是否建版本，需要明确编辑稿与正式版本；“同一道题”也不能只看语义相同。权限方面，题目被共享不代表回答可共享，root更不能形成对所有派生题的继承权限。

技术上，原题型校验只允许既定字段，直接把来源塞入questions会破坏兼容；原整卷PATCH能替换内容，新增选题接口不足以保证真实来源。单次读授权无法阻止撤权与选用的竞争。匿名键按问卷生成，不能直接给出跨卷独立人数；同卷两实例的答案数不能当人数，也不能用答卷数减答案行数计算未答。

运行上，旧环境未启用副本集，原备份manifest只核验四集合且假定演示样本不变。历史使用计数只能从迁移时存量和之后真实事件开始，无法恢复早已消失的记录。第一阶段工作目录与旧标签并不完全相同，因此保留当前代码和材料后再扩展，不重置或丢弃已完成成果。

交付后复查进一步发现了以下具体问题，修复与复测过程保留在[功能复查报告](recheck-2026-10-26.md)和[AI日志](ai-log.md)中。

| 问题 | 处理与验证 |
| --- | --- |
| 异常Unicode或超大整数可能在编码、存储边界形成500 | 补充输入规范化和拒绝路径，异常请求明确返回校验错误并验证未写入 |
| 停止新选用的版本与本人已持有快照的访问边界容易混淆 | 分开验证源版本访问权限和本人问卷历史统计，既阻止越权又保留合法旧结果 |
| 收藏整理可能出现响应404但标签已提交，或归档后错误限制已有收藏改标签 | 将响应投影与标签写入置于同一事务，区分已有收藏整理和新增收藏/换版本 |
| 保存期间继续输入可能被响应覆盖，旧编辑页也可能覆盖新内容 | 保存期间限制继续编辑，失败保留输入；两个预先打开页面的实际冲突与版本数核对通过 |
| 历史关联缺失时误取最新版、同内容跨题假映射 | 固定明确来源身份，迁移及绑定同时核对题目、版本、root和快照，不按内容相同自动认定同题 |

测试夹具、错误码断言和浏览器异步等待也曾失败，修正后重新执行；这些工具问题与产品缺陷分别记录，原始失败没有被最后成功截图替换。真实操作中“没有找到回答校验”经截图确认是已建题仍为单选，版本修改说明为空则由用户确认忘填，均未误记为程序缺陷。

## 9 解决方法与实际边界

通过持久编辑稿、不可变版本、明确快照引用及发布标记统一编辑语义；通过独立ID和直接来源保留谱系，精确versionId作为默认统计键；通过本人scope和维护者受限计数入口分开题目使用与答卷访问。

以questionRefs承载来源元数据，保持旧题目和答案格式；原PATCH加入内容一致性检查，选用、升级和发布在各自事务中维护快照、usage及控制记录。正式升级从停写后的备份恢复到独立副本集，再执行dry-run、apply、重复迁移和前后核对；原27017库继续保留。新环境初始化演示数据与恢复已有业务库是两个入口，具体步骤和归档时间节点见[数据说明](data.md)及[迁移说明](migration.md)。

本阶段不自动识别同义题，不默认跨版本或派生合并，不做整库共享、无授权跨用户答卷统计、跨卷去重总人数、合并答卷明细或导出，也不物理删除正式历史。个人标签将来若升级共享容器，仍需身份映射、成员及授权迁移。查询超过资源上限明确拒绝，单节点副本集用于本机事务演示，不宣称生产高可用或无限规模。

项目完成以八项原文需求、旧功能回归、原数据延续、实际恢复和真实AI使用记录共同支撑。提交材料包含源码及schema/配置、四类技术文档、带步骤/输入/输出/结果的测试，以及本报告九项主题和八点演进；查看入口为[第二阶段材料索引](../submissions/stage2/README.md)。
